## Minimal First Target

The smallest useful first target should be backend-only and intentionally not DD-report-class.

Concrete target:

- Slug: `governed-memo-mini`
- Path: `programs/governed-memo-mini/`
- Modes: `intake -> draft_memo -> complete`
- Terminal: `[complete]`, matching observed current SimoneOS examples
- Patterns: `control-plane-standard`; optionally one `two-step-phase-gate` from `intake` to `draft_memo` if the phase wants to exercise confirmation composition
- Channels: `user_messages` or `user_text`, `system_mode_entry`, `widget_output`; no `frontend_intake`, no file upload, no child delegation
- Stage: one `llm-reasoning` action in `draft_memo` that produces a structured memo payload from recorded intake facts
- Artifact: a single domain artifact object at `work.memo_artifact` with `id`, `kind: "markdown"`, `title`, `body`, and `status`
- Registration: target-native `createProgramEntry()` using `loadSpecWithPatterns`, `enableNotebook`, `enableSimoneSkills` only if permitted by the target import surface, a projection builder, manifest/presentation metadata, and no frontend spec path unless a frontend is actually emitted
- Tests: colocated `programs/governed-memo-mini/__tests__/spec-load.test.ts` and `projection.test.ts`; no `*live*` or `*e2e*` test files
- QC: no `qc/facts`, no `qc/e2e-frontend`, no `qc/e2e-coverage.yml` entry, and no V2 roster entry in phase 1 because the program has no frontend

Why this is minimal:

- It exercises the hardest backend translation seam: foundry stage model to SimoneOS composed spec plus external projection/registration.
- It avoids document upload, eRoom integration, delegation fan-out, approval loops, frontend widget catalog, DOCX runtime registration, and live UAT.
- It should still satisfy the eventual acceptance ladder for a non-frontend program: `npm run qc:onboard`, `npm run specs:loadcheck`, `npm run typecheck`, and the program `__tests__`.

This does mean `qc:onboard` must be green with a non-user-facing generated program. If SimoneOS policy requires every registered program to be user-facing, that is a SimoneOS-side product policy blocker, not a foundry synthesis problem; the smallest unblock would be a documented "backend-only program" convention or an explicit QC exemption lane.

   Smallest unblock: either add a manifest strategy such as `semantic_patch` with target-owned patch anchors, or add SimoneOS auto-discovery for program entries and loadcheck.

2. Spec model mismatch. Foundry stages currently render from a generic standalone skeleton (`/tmp/pgas-new-gap1-attach-ywrSNu/programs/governed-memo-mini/specs.yml:1-131`) and the synthesizer mechanically derives mode/action/schema blocks from its internal stage model (`/home/simone/pgas-new/src/foundry-program/synthesizer.ts:442-728`).    Smallest unblock: introduce a translation layer from foundry stage archetypes to target patterns, rather than adding more one-off YAML templates.

Foundry can write/merge `qc/e2e-coverage.yml`, facts, and scenarios, but SimoneOS protects QC files/dirs through integrity and drift fingerprints (`/home/simone/simoneos/qc/integrity.ts:32-76`; `/home/simone/simoneos/qc/drift-check.ts:49-132`).    Smallest unblock: governed attach must execute target-owned update commands in scratch after rendering, or it must stop at a curator request and not claim the acceptance target.

It declares a user-facing frontend program and fee-proposal facts/scenario without emitting a frontend spec (`/tmp/pgas-new-gap1-attach-ywrSNu/qc/facts/governed-memo-mini.facts.yml:1-23`; `/tmp/pgas-new-gap1-attach-ywrSNu/qc/e2e-frontend/governed-memo-mini.scenario.yml:1-28`).

   Smallest unblock: governed attach should pin/test against the target repo's installed server package, not only pgas-new's own pinned version.

Inferred blockers:

1. Full DD-report requires repo-specific integration surfaces that the current SimoneOS manifest does not declare. The manifest has research/document-ingest/review-service only (`/home/simone/simoneos/.pgas/wiring.yml:27-42`), while DD-report behavior needs eRoom ingest, document DD child sessions, batching, section assembly, sync-out, and DOCX frontend registration.
   Smallest unblock: extend `.pgas/wiring.yml` with explicit eRoom integration and available `document-due-diligence` service contract before asking the foundry to synthesize that flow.

2. Automatic integrity rotation from an external foundry is governance-sensitive. It may be technically possible, but SimoneOS may require those rotations to be run inside the repo by a trusted curator action.
   Smallest unblock: define whether foundry-rendered QC rotations are acceptable and what audit reason format must be used.

3. "Governed attach" is a target-specific compiler mode. If pgas-new tries to keep one universal existing-repo scaffold, it will keep producing standalone artifacts that happen to be placed in another repo. The smallest sustainable design is a generic attach core plus target governance adapters, starting with `simoneos`.

## Verdict

Governed SimoneOS attach is achievable incrementally, but not through the current `render-attach` output with small cosmetic changes. The key work is a target governance layer: stage-to-pattern spec translation, target-native registration patches, projection generation from the real domain contract, QC/drift/integrity handling, and frontend synthesis later.

Recommended delivery shape:

- Backend-only governed minimal program: 5 PRs, medium to large total effort.
- Frontend-enabled governed minimal program: add 1 large PR after Gap 10.
- DD-report-class generation: add 1 XL scale-up PR after frontend and manifest/integration unblocks.

Total rough effort: 6-7 PRs for credible governed attach through a frontend-capable minimal program; 7-8 PRs to reach DD-report-class. The single biggest blocker is target-owned mutation of SimoneOS static registration/loadcheck/QC integrity surfaces. If SimoneOS does not allow foundry-owned semantic patches or auto-discovery, governed attach can only emit curator requests, not passing branches.
